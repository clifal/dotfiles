# env-audit

起動: `/env-audit [dotfiles のパス]`

ローカルの設定ファイルは手元で育ち、リポジトリは置いていかれる。この skill は、その差を洗い出してリポジトリへ戻し、ついでに溜まったキャッシュを落とす。パスの既定は `~/repo/personal/dotfiles`。

掃除は消す作業なので、候補を出すところまでを自分でやり、消す前に必ず承認を取る。承認の範囲を超えて消さない。

## 1. 差分を洗い出す

`git ls-files` で追跡中のファイルを列挙し、1 つずつローカルの実ファイルと `diff` する。対応先は配置手順を書いた README から読む。推測しにくいものだけ挙げる。

- `.claude/` → `~/.claude/`
- `karabiner/`、`markdownlint/`、`mise/` → `~/.config/<同名>/`
- `vscode/vscode-keybindings.json` → `~/Library/Application Support/Code/User/keybindings.json`
- `zsh/.zshrc`、`zsh/.zshenv` → `~/`

ファイルどうしの `diff` では見えない差分が 3 つある。それぞれ専用の手段で比べる。

- Brewfile: `brew bundle dump --file=<一時ファイル> --force` を取って `diff`。`--describe` は無効化されているので付けない（既定で説明のコメントが入る）
- VS Code 拡張: `code --list-extensions` と Brewfile の `vscode "..."` 行を突き合わせる
- VS Code の設定: リポジトリにあるのは断片なので、断片に出てくるキーだけを実物と比べる

## 2. 反映するものを仕分ける

洗い出した差分を 4 つに分ける。

- 反映する
  - ローカルで実際に設定を変えた結果
- 伏せ字のまま残す
  - リポジトリ側が意図的にプレースホルダにしている箇所
  - `USERNAME`、`COMPANY-NAME`、`123456789`、`private-ssh-key` が代表で、実値で上書きしない
- 環境ごとの設定として無視する
  - `settings.json` の `effortLevel` と、`modelSettings` の各モデルの `effortLevel`
  - マシンごとに値を決めるので、リポジトリと食い違っていても反映せず、報告にも挙げない
- 判断を仰ぐ
  - ツールが自動で書き足した行、外部管理のファイル、シンボリックリンクで入ってきたもの

4 つ目は自分で決めず、1 回にまとめて聞く。聞き方は選択肢の形にし、推奨を先頭に置く。絶対パスを含む行を反映するときは `~` 表記へ直してから入れる。

## 3. 反映する

リポジトリ側を書き換える。ローカル側を変えた項目があれば、両方が一致した状態で終える。JSON を編集したらパースを通して確かめる。

設定ファイルを書き戻すアプリが動いていると上書きが消える。Karabiner-Elements のように常駐するものは、プロセスの有無を確かめてから触る。

## 4. README を追従させる

README は設定値を散文で説明しているので、値を変えた箇所は本文も直す。変えた値を `grep` して、言及しているすべての段落を拾う。

次の 3 つは本文に書かれた数値や手順なので、実測と突き合わせて直す。

- プラグインのスキル数と常時消費トークン: `claude plugin details <プラグイン名>` の `Always-on`
- 除外しているディレクトリの容量: `du -sh`
- 外部スキルの導入コマンド: 実体がコピーかシンボリックリンクかで引数が変わる

直したら markdownlint を通す。既存のエラーが残っている文書なので 0 件を目指さない。編集前の版を `git show HEAD:<path>` で取り出し、エラー件数が増えていないことだけを確かめる。

## 5. 掃除候補を出す

容量の大きい順に当たる。再生成できるキャッシュと、消すと状態が失われるものを分けて示す。

| 対象 | 確かめ方 |
| --- | --- |
| Homebrew | `brew cleanup -s --prune=all -ns` で見積もる。`-s` だけでは cask の downloads が残る |
| npm | `npm cache clean --force` は `_cacache` しか消さない。`~/.npm/_npx` は別に消す |
| pnpm | `pnpm store prune` |
| puppeteer | `~/.cache/puppeteer` に版が溜まる。最新を 1 つ残す |
| Claude のプラグイン | `~/.claude/plugins/cache/` の旧版。`installed_plugins.json` の `installPath` に無い版だけ |
| mise | **消す前に `~/.local/state/mise/tracked-configs` を読む**。旧版に見えてもプロジェクトの `mise.toml` が固定していることがある |

mise の罠は実際に踏みかけた。`~/.config/mise/config.toml` が `latest` でも、別のリポジトリが具体的な版を固定していれば、その版は現役である。`mise prune --dry-run` が何も出さないときは、本当に消せるものが無い。

会話ログ（`~/.claude/projects/`）は `cleanupPeriodDays` が面倒を見る。保持期間を超えたファイルの数と容量を確かめ、機能しているなら候補に挙げない。

## 6. 承認を取って掃除する

候補の一覧と削減量を示し、承認を待つ。状態を持つもの（VM のディスク、コンテナ、データベース）は、容量が大きくても独立した判断として分けて聞く。

承認後は 1 つずつ実行し、前後の容量を測って報告する。見積もりではなく実測を出す。

洗い出しから承認までの間にユーザーが設定を変えていることがある。古い候補一覧をそのまま実行せず、承認された項目が今も有効かを確かめる。食い違ったら、その項目だけ手を止めて確認する。

## 7. memory を点検する

`~/.claude/projects/<プロジェクト>/memory/` を見る。

- `name:` とファイル名が一致しているか
- `[[リンク]]` の指す先が実在するか
- `MEMORY.md` の索引と実ファイルに過不足がないか
- 本文が参照している実体がまだ有るか。消したツールや外したスキルが例示に残りやすい

リンク切れは、未作成のメモを指す印として許される。残すか消すかはユーザーに聞く。

## 完了条件

- 追跡中のファイルがすべて、ローカルと一致するか、伏せ字か環境ごとの設定として残す理由が付いている
- README に残った記述が実測と合っている
- 掃除は承認された項目だけが実行され、前後の実測が報告されている
- memory の 4 点がすべて整合している
