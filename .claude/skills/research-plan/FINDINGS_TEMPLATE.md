# 調査結果テンプレート

Research 系 skill の背景エージェントが `research/<topic>/findings.md` を書くときの雛形。依頼書（plan.md）の 8 章から参照される。依頼書 8 章に個別の指定があれば、そちらを優先する。

## 構成の規約

- 章の並びは「0. 前提 → 1. 一覧表 → 対象ごとの章 → 出典」。出典を最後の章にする。GitHub などのレンダラーは脚注を文末にまとめて描画するので、出典章が末尾にあれば表示と章順が揃う。
- 調査対象が複数なら、対象ごとに 1 章を立て、章内の節を RQ の順に並べる。節番号 `N.k` の `k` は RQk に対応させ、見出しには RQ 番号ではなく主題を書く（例: `### 2.1 ライセンス`）。対象が 1 つなら、RQ ごとに 1 章を立てる。
- 未解決の項目は関係する章の最後の節（例: `### 2.6 未解決`）に置く。項目は `#### 2.6.1 <項目名>` と番号を振り、本文からは「（未解決 2.6.1）」で参照する。複数の対象にまたがる項目は対象ごとに分ける。調査方法そのものの制約は `method.md` に書く。未解決が無い章にも節を立て、「未解決の項目は無い。」と書く。
- 依頼者に判断を仰いで決まった事項は、0 章に結論だけを書き、未解決から外す。決定日は `method.md` に書く。

## 記述の規約

- 一次情報で確かめた事実だけを書く。原因や理由を補う文（「〜のため」「〜と考えられる」）も推測に当たる。一次情報で確かめられないことは、未解決に回す。
- 「無い」は根拠の強さで書き分ける。
  - 公式ドキュメントが非対応と記載している → 非対応
  - 公式ドキュメントに記載が無い → 記載無し
  - 製品や提供を探したが見つからなかった → 確認できず
- 状態を表す語は 0 章で定義し、表のセルも本文も同じ語で書く。各対象が使う中間段階（alpha、beta、private preview など）の割り当ても 0 章で決め、元のラベルを括弧で併記する。
- 箇条書きではラベルの行の下に値をネストする。「ラベル: 値。補足」と 1 行に詰めない。1 行には 1 つの事実だけを置き、行末に句点（。）を付けない。出典は値の行の末尾に半角空白を挟んで付ける。値が複数あって出典を共有するときは、ラベルの行に付ける。

  ```markdown
  - 現行ライセンス
    - AGPL-3.0-only [^1][^2]
      - `LICENSING.md` に "The default license for this project is AGPL-3.0-only" とある
  ```

- 表の 1 列には 1 種類の値だけを入れる（例: 方向の列と状態の列を分ける）。出典の列は作らず、脚注は状態などの説明の列の 1 行目の末尾に付ける。補足は同じセルの中で `<br>` で改行して続ける。セルの末尾に句点を付けない。

  ```markdown
  | プロトコル | 方向 | 状態 |
  | --- | --- | --- |
  | OTLP | 送信 | 記載無し [^3]<br>自身の HTTP API のトレースを OTLP で送る |
  ```

- URL を本文に書くときは `<https://...>` で囲む。
- 見出しや状態の語、脚注から読み取れることは書かない（例: 「本書はこの表記に従う」、導入手段の一覧に添えた「公式手順が有る」、「安定」の行に添えた「安定性保証の対象」）。
- 文書そのものについての情報は書かない。冒頭の依頼書パス・調査日・調査深度、「本書は〜を扱う」のような文書の紹介、「根拠は N 章にある」「出典は脚注で示した」のような章の案内が該当する。アクセス日は各脚注に、調査方法は `method.md` にあるので重複になり、読み手のノイズになる。
- 同じ概念は文書全体で 1 語にする。日本語で通じる語は日本語に揃える（リリース、バージョン、パッチリリース、公式ドキュメント、ページ、該当 / 非該当、有り / 無し）。原語のほうが通じる語と、各製品が使う固有のラベルは原語のまま書く（LTS、feature flag、製品名、ライセンス名、設定キー）。
- 件数や頻度を出したときは、数える単位、期間（タイムゾーン付き）、含めるものと含めないものを、その数値を出した節に書く。取得手段は `method.md` に書く。

## 0 章の規約

0 章には、本文を読むのに要る約束だけを置く。対象バージョン、状態の語、依頼書の語と一次情報の語がずれる用語の 3 つで、本文で使わないものは節ごと消す。

## 調査記録（method.md）の規約

調べ方の記録は `research/<topic>/method.md` に分け、findings.md には書かない。findings.md の読み手は結果を使う人で、調べ方は要らない。method.md は調査をやり直すときや、結果の信頼性を確かめるときに読む。

- 依頼書のパス、調査日、調査深度
- 対象バージョンの選び方（例: GitHub Releases からプレリリースを除いた最新）
- 取得手段（使った CLI、API、行番号の基準にしたタグ）
- 依頼者に判断を仰いだ事項と決定日
- standard 以上: Tier ごとの出典の件数と一次ソース比率
- deep: 検証の方法、件数（検証・一致・修正・裏が取れず）、修正した箇所の前後、裏が取れなかった項目の扱い
- 調査方法そのものの制約（取得手段の制限、数え方の限界）を、未解決と同じ 3 点で

## 出典の規約

- 出典は脚注 `[^n]` で付ける。`n` は本文に初めて出る順に振る。1 つの出典には 1 つの脚注だけを定義し、同じ出典は同じ番号で何度でも参照する。
- 定義は出典章に `[^n]: タイトル / 公開日または更新日 / Tier / <URL> / アクセス日` の形で並べる。
- 複数の出典は `[^1][^2]` と続けて並べる。括弧や読点で囲まず、`[^1]〜[^6]` のような範囲表記も使わない。
- 出典の URL は脚注の定義にだけ書く。本文に直接書いてよい URL は、出典ではない参照先（未解決の「次に何を見れば埋まるか」など）に限る。

## 書き上げ後の仕上げ

背景エージェントの報告を受け取った親エージェントが行う。

1. 背景エージェントがファイルを書けずに本文を返した場合は、その本文をそのまま `findings.md` に保存する。
2. 上の規約を満たしているか確かめる。method.md が書かれているかも確かめる。次の 5 点は機械的に探せる。
   - 推測の語: `推測|思われ|おそらく|可能性|だろう`
   - 本文中の生の URL のうち、脚注の URL と重なるもの
   - 脚注番号が初出順になっているか
   - 状態を表す語の揺れ
   - 文書そのものについての記述: `本書|依頼書|調査深度|章にある|脚注で`
3. `/refine-doc` を compress モードで実行し、500 字を超える節を 85〜90% に詰める。suiko full は refine-doc の中で実行される。脚注の定義だけの出典章は、URL と日付が保持域なので帯に入らなくてよい。

完了条件: 3 つの手順がすべて終わり、refine-doc の完了条件（帯外の節の理由、保持域の差分 0、suiko の finding の採否と理由）が満たされている。
