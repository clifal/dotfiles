# slides

スライドはこの skill のテンプレート（`assets/template.pptx`）のレイアウトの上に、python-pptx で直接組む。規約と検査は consulting-pptx-skill のものを使い、組み方はその slide-rules §8.7（既存の資料に差し込むページ）に従う。そのスキルが既定とする作り方（HTML で組んで PPTX に変換する）では、書体と版面がテンプレートからずれる。

consulting-pptx-skill の決まりのうち、Jinba の扱い（`references/jinba-context.md`）と、最終ページに作成ツールの注記を入れる決まりは使わない。出典行には元の文書の節番号だけを書く。

デッキごとに 1 つのフォルダ（デッキのフォルダ）を作り、組み立ての道具、記録、渡すファイルをまとめて置く。置き場所は依頼者に合わせ、決まりがなければ作業中のプロジェクトの `slides/<デッキ名>/` にする。

- `build.py`: ページの中身。`scripts/house.py` の部品で組む。見本は `examples/sample/build.py`（架空の題材で、表紙・目次・章扉 3 枚＋本文 7 枚）
- `sources.md`: デッキに載せた数字の控え。何の数字か、節番号、実績・想定・見積の別、試算の式と結果
- `qa.md`: 検査と、ページごとの目視の記録
- `review.md`: フレッシュアイ・レビューの採否表
- `<題>.pptx` と `<題>.pdf`: ファイル名は表紙の題と同じにする。版（α版、β版、確定版など）は題に入れる。作業中の手直しは同じ名前に上書きしてよい

## 準備

```sh
git clone https://github.com/carnot-tech/jinba-consulting-pptx-skill.git ~/.claude/skills/consulting-pptx-skill
pip3 install python-pptx pillow
brew install poppler
```

- 書体の BIZ UDGothic を入れる。macOS は Font Book で「BIZ UDGothic」をダウンロードし、Windows 10 以降は最初から入っている
- PDF の書き出しに Keynote を使う
- 文言の推敲に yomiyasu プラグインを使う
- consulting-pptx-skill を別の場所に置いたときは、環境変数 `CONSULTING_PPTX_SKILL` にそのフォルダを入れる。この skill を別の場所に置いたときは、`SLIDES_SKILL` にこの skill のフォルダを入れる

## 1. 決める

読み手と場面を決める。決まっていなければ聞く。

ページは元の文書の章立てに合わせて並べる。

- 元の Markdown の、番号の付いた H1 ごとに章扉を置く。付録（番号のない H1）は章にせず、本文の出典の行で示す
- 本文は 1 章 2〜4 枚を目安にし、章の Markdown の字数（空白を除く）で決める。8,000 字未満は 2 枚、8,000〜15,000 字は 3 枚、15,000 字を超えると 4 枚。依頼者の合意があれば目安を超えてよい
- 表紙のあとに目次を置く。表紙、目次、章扉は本文の枚数に数えない
- 元の文書が章ごとに結論を述べているときは、結論だけを並べたサマリーのページを置かない。目次のすぐあとに結論が来ると、流れが不自然になる
- 章ごとの枚数と各ページの中身（題、載せる節、見せ方）は、組む前に依頼者に確かめる

題とファイル名は、毎回ここで確かめる。

1. 題の案を自動で決める。作り直しなら、前回の `build.py` の `TITLE` を案にする。新しいデッキなら、元の文書の題に、文書の版を括弧で添える（α版、β版、確定版など）
2. ファイル名の案は題と同じにする（`<題>.pptx` と `<題>.pdf`。`house.deck_path` が作る）
3. AskUserQuestion で 1 回だけ聞く。質問文に題とファイル名の案を書く。選択肢の 1 つ目は「この題とファイル名で作る（推奨）」、2 つ目は版だけを変えた題にする。違う題にしたいときは「Other」に入力してもらい、入力された題からファイル名を作り直す
4. 確かめた題を `build.py` の `TITLE` に書く。表紙の題も `TITLE` から作られる

依頼の中で題を指定されたときは、それを案の代わりに使い、聞き直さない。表紙の宛名（`ORG`）、作成者（`BY`）、フッターの 1 行（`FOOTER`）も、同じ質問で確かめる。

作り直しは前回の `build.py` を元にし、元の文書の変わったところだけを直す。数字と文言は、前回のデッキからではなく元の文書から取り直す。

新しいデッキは consulting-pptx-skill の `python3 scripts/rules.py --phase plan` を読み、タイトルの列（ストーリーライン）を書いて依頼者の合意を取る。

完了: 題とファイル名を確かめ、`TITLE` に入れた。章ごとの枚数とタイトルの列に依頼者の合意がある。作り直しで構成を変えないときは、変える箇所の一覧に合意がある。

## 2. 材料をそろえる

元の文書を読み、載せる数字を `sources.md` に 1 行ずつ控える。試算は `python3 -c` で計算し、式と結果を貼る。人は役割名で書く（「窓口の担当」など）。元の文書が伏せた名前は、伏せたまま書く。

完了: デッキに載せる数字がすべて `sources.md` にあり、節番号で原文に戻れる。

## 3. 組む

書く前に、consulting-pptx-skill の `rules.py --phase build` と `--phase text`、ページの形に応じて `--phase table`／`chart`／`process` を読む。版面、色、ページの形ごとの部品は [design.md](design.md) にある。

新しいデッキは `examples/sample/build.py` をデッキのフォルダへ写して始め、`TITLE`、`ORG`、`BY`、`FOOTER`、`DOC` とページの関数を書き換える。

```sh
python3 -I <デッキのフォルダ>/build.py
```

デッキのフォルダに `<題>.pptx` ができる。ファイル名は空白と全角の括弧を含むことが多いので、シェルでは引用符で囲む。

ページの並びは `build.py` の末尾の `FRONT`（目次）と `CHAPTERS`（章の番号、章題、扉の副題、本文のページ）で決める。本文で別のページを指す「P.n」は `b.ref(ページの関数)` で書く。並びから数えるので、ページを足しても減らしても参照はずれない。

完了: PPTX ができ、タイトルが全ページで全角 39 字以内に収まっている。

## 4. 要点が伝わるかを確かめる

PDF にする前に、新しく書いたページと直したページを、元の文書の節と読み比べる。版面ではなく、伝える中身を見る。

- 元の節の要点（結論、太字の箇所、数字に付いた条件）がページに残っているか。短くするときに、判断に要る条件（誰が、いつまでに、何を前提に）を落としていないか
- 用語を、初めて出るページか、それより前のページで説明しているか
- 見出しと、その下に置いた中身が合っているか

ページを消したときは、そのページにしかなかった説明と注が、残るページのどこかにあるかも確かめる。消したページで説明していた用語は、ほかのページで説明なしに使われたままになりやすい。

完了: 新しく書いたページと直したページのすべてを元の節と読み比べ、`qa.md` に結果がある（落ちていた要点と直したこと。なければ「該当なし」）。

## 5. 文言を推敲する

PDF にして見る前に、文言を yomiyasu に通す。新しく書いたページと直したページを書き出す。

```sh
python3 -I ~/.claude/skills/slides/scripts/export_text.py "<pptx>" <スクラッチ>/text.md [ページ番号,...]
```

書き出したテキストを `yomiyasu:yomiyasu` に `--full` で通す。種類は slides、資料には元の文書を渡す。採った直しを `build.py` に戻して組み直す。検査の出力の「消えた語」に要点の語があれば、4 に戻ってそのページを直す。

完了: yomiyasu の verify がハッシュの一致を返し、採った直しが `build.py` に入っている。

## 6. 検査する

```sh
python3 -I ~/.claude/skills/slides/scripts/check.py "<pptx>"
```

完了: FAIL が 0 で、残る WARN が [quirks.md](quirks.md) に挙げた既知のものだけ。溢れの候補が出たページは、7 で必ず見る。

## 7. PDF にして全ページを見る

```sh
python3 -I ~/.claude/skills/slides/scripts/render.py "<pptx>" <スクラッチ>/sheets
```

PDF は PPTX の隣に出る。4 ページずつ並べた画像をすべて見て、consulting-pptx-skill の `rules.py --phase check` の基準を当てる。崩れを直したら 6 からやり直す。Keynote が応答しないとき、Keynote が使えないときは [quirks.md](quirks.md) を見る。

完了: 全ページを見て、`qa.md` に各ページの結果がある（見つけた崩れと直したこと。なければ「該当なし」）。

## 8. フレッシュアイ・レビュー

[fresh-eye.md](fresh-eye.md) の手順で、文脈を持たない別のエージェントに PDF を読ませる。最低 2 回回す。1 回目の採用分を直して 5〜7 をやり直してから、2 回目を回す。2 回目までは止めずに続け、3 回目を回すかは依頼者に聞く。

完了: `review.md` に 2 回分以上の採否表があり、回ごとに採用した直しを入れて 6 と 7 をやり直した。

## 9. 渡す

PPTX と PDF の両方がデッキのフォルダにあることを確かめる。題を変えたときは、古い名前のファイルを消すかを依頼者に聞く。コミットと、ダウンロードフォルダなどへのコピーは、頼まれてから行う。

## 終わったと言える状態

- 題とファイル名を依頼者に確かめてある
- `check.py` が FAIL 0 で、残る WARN が既知のものだけ
- 新しく書いたページと直したページを元の節と読み比べ、要点が残っていることを `qa.md` に書いた
- 最新の PDF で全ページを見て、`qa.md` に書いた
- 載せた数字がすべて `sources.md` にあり、原文と合う
- 新しく書いた文言と直した文言を、yomiyasu に通した
- フレッシュアイ・レビューを 2 回以上回し、回ごとの採否表がある
- デッキのフォルダの Markdown が `npx markdownlint-cli2` を通る
