# software-guide

起動: `/software-guide <ソフトウェア名> [出力先ディレクトリ]`

ソフトウェア1つについて、ジュニアエンジニアが一読で全体をつかめる入門ガイドを作る。成果物は次の4つで、すべて出力先ディレクトリに置く。

- `<slug>-guide.md`: 本文
- `images/<slug>-overview.svg` と `images/<slug>-overview.png`: インフォグラフィック
- `research-notes.md`: 出典付きの調査メモ

`<slug>` はソフトウェア名を英小文字ケバブケースにしたもの（例: `Grafana` → `grafana`、`Apache Kafka` → `apache-kafka`）。出力先ディレクトリの既定は、作業ディレクトリ直下の `<slug>/`。ソフトウェア名が引数に無ければ、何を対象にするかだけ聞いてから始める。

## 1. 調査を背景エージェントに出す

`mattpocock-skills:research` を起動し、その手順どおり背景エージェントに調査させる。依頼文は、この skill の `research-plan.md` の `{{NAME}}`、`{{OUT_DIR}}`（出力先の絶対パス）、`{{DATE}}`（今日の日付）を埋めた全文にする。背景エージェントは会話の文脈を持たないので、依頼文を要約しない。

エージェントの報告が届き、`research-notes.md` が出力先にできたらこのステップは完了。届くまでは、ステップ2の図の枠組み（色、配置、タイトル）だけ先に作ってよい。図の中身は調査結果で決まるので、報告前に埋めない。

## 2. 図解画像を作る

`research-notes.md` を全部読んでから作る。図は1枚のSVGで、1200×800を基準にする。構成と見た目は `assets/overview-example.svg`（Grafana で作った実例）に合わせる。

- 上段: 対象ソフトウェアを中央に置き、左に入力（データソース、接続先、利用者の操作など）、右に出力（画面、通知、生成物など）を置いて矢印でつなぐ。入力と出力の中身は、調査メモの「概要」と「使い方」から取る。
- 下段: 「はじめて使うときの流れ」を4ステップで並べる。本文の「使い方」の4つの見出しと同じ順・同じ名前にする。
- 文字は図のラベルなので、短い言い切りや体言止めでよい。フォントは `'Hiragino Sans', 'Hiragino Kaku Gothic ProN', 'Noto Sans JP', sans-serif`。

SVGをヘッドレス Chrome で PNG にする。

```sh
cd <出力先>/images && "/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" \
  --headless=new --disable-gpu --hide-scrollbars --force-device-scale-factor=2 \
  --window-size=1200,800 --screenshot=<slug>-overview.png "file://$PWD/<slug>-overview.svg"
```

`CVDisplayLinkCreateWithCGDisplay failed` のエラー行は出ても無視してよい。できた PNG を Read で開いて目で確かめ、文字のはみ出し、重なり、枠からの欠けが1つも無くなるまで SVG を直して再出力する。

## 3. 本文を書く

`guide-template.md` の見出し構成をそのまま使い、`<slug>-guide.md` に書く。コメント（`<!-- -->`）は各節に書く内容の指示なので、書き終えたら消す。

書き方の決まり:

- 文体は「です・ます」。読者はジュニアエンジニアで、専門用語は初出で一言説明する。
- 見出しの直後から本文を始める。ガイドの目的や対象読者を述べる前置きの段落は書かない。
- 事実、数値、バージョン、日付、コマンドは `research-notes.md` にあるものだけを使う。メモで「未確認」になっている事柄は本文に書かない。
- コマンドに前提条件（別のソフトウェアが動いていること等）があれば、コマンドの直前に書く。
- 太字は本文全体で1〜2箇所。画面のボタン名やメニュー名は「」で囲む。
- 箇条書きは並列の項目（機能一覧、選び方の目安、参考リンク）に限り、理由や条件を含む説明は地の文にする。
- 表の区切り行は `| --- | --- |` の形にする（markdownlint の MD060 対策）。
- 日本語と英単語・数字の間に半角空白を入れない（例: 「Grafanaは」「2026年」「50GB」）。見出しとコードは除く。

## 4. レビューする

書いた本文を `research-notes.md` と突き合わせる。次の全項目を確かめ終えたら完了。

- 本文の数値・バージョン・日付・ライセンス名がすべて調査メモと一致している。
- 調査メモに無い主張が本文に1つも無い。
- 各コマンドが、書かれた前提条件のもとで実際に動く形になっている。
- 「使い方」の4つの見出しが図の下段と一致している。
- 比較表の各行が、調査メモで landscape 掲載を確認できたものになっている。

見つけた問題はその場で直す。

## 5. yomiyasu で添削する

元の本文をスクラッチパッドへ退避してから、`yomiyasu:yomiyasu` を `tech --full <本文の絶対パス>` で起動し、その手順どおりにリンターと Diff 検査（`--stance=説明`）まで通す。

書き直しは一括で受け入れず、変更ごとに採否を決める。「です・ます」調では、同じ文末が3回続くという警告が出やすい。文が自然に読めているなら、警告を消すためだけの言い換えはしない。

## 6. 報告する

ユーザーには次の点だけを短く伝える。

- 作ったファイル（本文、画像、調査メモ）のリンク
- レビューと yomiyasu で直した主な点
- 調査メモで「未確認」のまま残った事柄
