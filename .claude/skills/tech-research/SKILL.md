# 技術調査レポート

Webの一次ソースを根拠に、数値と出典が検証された技術調査レポートを作成する。

## 引数

テーマのみを受け取る。調査深度と出力先はステップ1でまとめて確認する。ユーザーが引数で深度や出力先を指定した場合はそれを初期値としてステップ1に持ち込む。

## 調査深度

| 深度 | 大項目数 | 並列数 | ソース階層 | 一次ソース遡及 | 独立検証 |
|---|---|---|---|---|---|
| quick | 3-5 | 3 | Tier 1 のみ | なし | なし |
| standard | 5-8 | 3-5 | Tier 1 / 1.5 / 2 | 数値のみ | あり（1巡） |
| deep | 8-12 | 3-5 | Tier 1 / 1.5 / 2 | 数値と記述の両方 | あり（2巡） |

デフォルトは standard。

quick で作成したレポートは、冒頭に次のバナーを必ず入れる。

```markdown
> ⚠️ 未検証ドラフト — quick 深度で作成。数値は一次ソースまで遡及していない。共有・引用の前に standard 以上で再調査すること。
```

## モデルの割り当て

subagent を起動するとき、Agent ツールの `model` を役割に応じて指定する。指定を省くと親と同じモデルが使われ、機械的な作業にも高価なモデルを充ててしまう。

| 役割 | model | 理由 |
|---|---|---|
| 調査 subagent（ステップ2） | `opus` | 一次ソースの取捨選択と Tier 判定が成果物の品質を決める |
| 検証 subagent（ステップ4） | `sonnet` | WebSearch で数値を照合する機械的な作業 |
| 整形・書き換えの subagent | `sonnet` | 情報の再配置のみで、判断を伴わない |

統合、目次設計、大項目間の矛盾の解消は親が行う。subagent に投げない。

## フロー

### ステップ1 — 目次案の承認

plan mode に入り、次の3点を提示して承認を得る。

1. 目次案（大項目と、各大項目に含める中項目）
2. 調査深度
3. 出力先ファイルパス

出力先はユーザーが指定する。指定がなければ提案し、承認を得る。出力先ディレクトリに `NN_*.md` 形式のファイルが既にある場合のみ、次の連番を採番して命名に使う。

目次案を作る前に、テーマの全体像を把握するための予備検索を1-2回行ってよい。ただしこの段階では本調査を始めない。

承認を得るまで次のステップに進まない。

### ステップ2 — 並列調査

大項目ごとに調査 subagent を1つ起動する。同時起動は3-5並列に抑える。大項目が6つ以上あるときはバッチに分ける。一斉起動はソースの重複取得とレート制限を招く。

各 subagent に渡すもの:

- 担当する大項目とその中項目
- テーマ全体の1段落説明（他の大項目と重複した調査をさせないため、他の大項目の見出しも併せて渡す）
- `SOURCE-TIERS.md` と `OUTPUT-FORMAT.md` を読むよう指示
- 結果の保存先パス（scratchpad 配下の `NN_大項目名.md`）

各 subagent の指示に必ず含めること:

- 調査結果は保存先パスに書き出す
- 親への返答は「保存先パス」と「1行要約」のみ。本文を返さない
- **Agent ツールを使わない。subagent をさらに起動しない**
- `ax` は必ず `--outline` かセレクタを付けて呼ぶ。ページ全文を取得しない
- 取得結果が長いときはファイルに保存し、`grep` / `sed` で必要箇所だけ読む
- ツール呼び出しは1大項目あたり40回程度を目安とする。超えそうなら、確認できた範囲で書き出して終える

親のコンテキストに全文を積むとコンテキストを使い切る。ファイル経由でやり取りする。

subagent が孫を起動すると、消費量が制御不能になる。実測では、再委譲を禁じなかった検証フェーズが1回の調査全体の38%を消費した。

`ax` で取得したページ本文は、以後そのエージェントの毎ターンでキャッシュ読み出しの対象になる。全文取得を繰り返すと、1つの subagent だけでキャッシュ読み出しが数百万トークンに達する。

### ステップ3 — 統合

scratchpad の各ファイルを読み、1つのレポートに統合する。

- 大項目間で重複した記述を排除する
- 脚注ラベルを `[^大項目番号-連番]` 形式に振り直す（`OUTPUT-FORMAT.md` 参照）
- 大項目の間で数値や主張が矛盾している場合は、この時点で解消する。解消できないときは両論を併記し、検証ステップに委ねる

各大項目の冒頭に2-3文の導入文を置く。文章の仕上げはステップ6でまとめて行うので、ここでは内容の統合に集中する。

### ステップ4 — 独立検証

quick では実行しない。

検証 subagent を起動する。**本文だけを渡す。参考URL一覧と脚注定義は渡さない。** 書いた本人が自分の拾ったソースを見ながら検証しても、確証バイアスで機能しない。

検証 subagent には `VERIFICATION.md` を読むよう指示する。あわせて、ステップ2と同じ制約（Agent ツールを使わない、`ax` はセレクタ付き、取得結果はファイル経由、ツール呼び出しの目安）を渡す。

検証対象の数値が多いときは、章を分けて2-3体の検証 subagent に並列で担当させる。1体に全章を渡すと時間内に終わらない。

deep では2巡実行する。1巡目で格下げ・置換された項目について、2巡目の subagent に再調査させる。

### ステップ5 — 検証結果の反映

検証 subagent の報告に従って本文を修正する。

- 数値が異なっていた → 検証側の値に置換する。元の値と置換後の値を付録Aに記録する
- 一次ソースが見つからなかった → その数値を `数値未確認` に格下げする。項目自体は残す。付録Aに記録する
- 全件が確認済みだった → 付録Aを生成しない

ユーザーに個別の判断を求めない。数十件になると承認疲れで素通しされる。

### ステップ6 — 日本語の仕上げ

統合と検証を終えたレポート全体に `suiko` skill を適用し、読解負荷を下げる。深度が deep の場合と、レポートが約1万字を超える場合は `full`、それ以外は `quick` を使う。

対象は散文だけとする。表、箇条書き、脚注定義、参考URL一覧、付録A、コードブロックは書き換えない。

`suiko lint` は箇条書き行を解析対象に含めない。レポートをそのまま lint すると見出しとラベル行だけが文として扱われ、`low_burstiness` や `uniform_paragraph_structure` の偽陽性が出る。散文の行だけを抜き出した一時ファイルを scratchpad に作り、そちらを lint する。

```sh
suiko lint <散文だけの一時ファイル> --genre tech --reading-load --experimental --json
```

`--experimental` は未校正の検出器を有効にする。閾値が校正されていないため finding が増えるが、採否はこちらで判断するので構わない。

finding を読む前に `doc_char_count`、`readability.particle_token_ratio`、`lexical_diversity.skipped_too_short` を確認する。文字数が実体とかけ離れている、助詞比率が0、`skipped_too_short` が true のいずれかなら、抜き出しに失敗している。

finding は機械的に消さない。次は書き換えの対象外とする。

- 数値、単位、日付
- 製品名、プロトコル名、識別子などの固有名詞
- 脚注ラベルと、その直前の被参照語
- Tier 判定や `数値未確認` の格下げに関わる表現

検証済みの数値と出典の対応を崩す修正は却下する。採用した修正は元のレポートへ戻す。

### ステップ7 — 書き出し

承認された出力先に書き出す。冒頭のメタ情報に検証カバレッジ（`数値 42件中 38件が一次ソース確認済`）を記載する。

書き出し後、ユーザーには次を報告する。

- 出力先パス
- 大項目数と数値の件数
- 検証で格下げ・置換した件数

## subagent が失敗したときの扱い

レート制限やタイムアウトで subagent が失敗しても、**保存先ファイルが書けているかを必ず先に確認する**。書き出しを終えた直後の終了処理で失敗する場合があり、成果物は無傷なことが多い。

確認するのはファイルの存在と末尾で、`### 参考URL一覧` まで到達していれば完結している。完結していれば再実行しない。

失敗した subagent を無条件に再実行すると、同じソースを取り直して消費量が倍になる。

## 参照ファイルの読み分け

| ファイル | 読む主体 |
|---|---|
| `SOURCE-TIERS.md` | 調査 subagent、検証 subagent |
| `OUTPUT-FORMAT.md` | 調査 subagent、親（統合時） |
| `VERIFICATION.md` | 検証 subagent |

親は3つすべてを読む必要はない。ステップ3の統合時に `OUTPUT-FORMAT.md` を読めばよい。

## 使用ツール

| 用途 | ツール |
|---|---|
| ソースの発見 | WebSearch |
| ページ本文の取得・構造抽出 | `ax` CLI |
| ライブラリ・API・フレームワークの仕様 | Context7（クエリ末尾に `use context7`） |

`ax` はURLが既知であることを前提とするため、発見には WebSearch を使う。取得後の抽出は `ax <url> <selector>` や `ax <url> --outline` を使い、HTMLに正規表現をかけない。

## 禁止事項

- Tier 3 ソース（個人ブログ、SEOまとめ記事、AI生成記事、出典のないニュース）の引用
- 出典のない数値の記載
- 装飾目的の図
- ステップ1の承認を得ずに本調査を始めること
- 既存レポートの更新への転用（このSkillは新規作成専用）
