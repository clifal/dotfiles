# 技術調査レポート

Webの一次ソースを根拠に、数値と出典が検証された技術調査レポートを作成する。

すべての主張を、その事実を最初に公表した**所有者ソース**まで遡る。ブログや記事は所有者ソースへ至る経由地であり、脚注に載せるのは到達した原典である。探索順序は `SOURCE-TIERS.md` の「一次情報の探索順序」に従う。

## 引数

テーマのみを受け取る。調査深度と出力先はステップ1でまとめて確認する。ユーザーが引数で深度や出力先を指定した場合はそれを初期値としてステップ1に持ち込む。

## 調査深度

| 深度 | 大項目数 | 並列数 | ソース階層 | 一次ソース遡及 | 独立検証 |
|---|---|---|---|---|---|
| quick | 3-5 | 3 | Tier 1 のみ | なし | なし |
| standard | 5-8 | 3-5 | Tier 1 / 1.5 / 2 | 数値のみ | あり（1巡） |
| deep | 8-12 | 3-5 | Tier 1 / 1.5 / 2 | 数値と記述の両方 | あり（2巡） |

デフォルトは standard。

quick で作成したレポートは、冒頭に次のバナーを必ず入れる。

```markdown
> ⚠️ 未検証ドラフト — quick 深度で作成。数値は一次ソースまで遡及していない。共有・引用の前に standard 以上で再調査すること。
```

## モデルの割り当て

subagent を起動するとき、Agent ツールの `model` を作業の性質で決める。省略すると親と同じモデル（最上位・最高単価）が使われ、機械的な作業に最も高価なモデルを充ててしまう。

入力トークン単価の比は、おおよそ 親 10 : `opus` 5 : `sonnet` 2 : `haiku` 1。調査 subagent は1体で数十万トークンのページ本文を読むため、ここが総コストの大半を占める。

### 判定基準

- **判断**を伴う作業 → `opus`。ソースの取捨選択、Tier 判定、所有者ソースへの遡及、矛盾する数値の評価。成果物の品質を決める
- **照合**の作業 → `sonnet`。明確な基準（`VERIFICATION.md` の一致 / 不一致 / 発見不能）に沿って突き合わせる
- **変換**の作業 → シェルスクリプト（`sed` / `awk` / `grep`）。脚注の振り直し、散文の抽出、ファイルの結合。判断を伴わないものに LLM を使わない。スクリプトで書きにくいときだけ `haiku`
- **統合**（目次設計、大項目間の重複排除と矛盾解消、compress-doc の再構成と suiko の採否判断）→ 親が行う。subagent に投げない

1体の subagent の途中でモデルは変えられない。判断と変換が混じる作業は、判断の部分だけを subagent に切り出し、変換は親がスクリプトで済ませる。

### 作業別の割り当て

| 作業 | 深度 | model | 理由 |
|---|---|---|---|
| 調査 subagent（ステップ2） | quick | `sonnet` | Tier 1 のみ・遡及なしで、取捨選択の余地が小さい |
| 調査 subagent（ステップ2） | standard / deep | `opus` | Tier 判定と所有者ソースへの遡及が品質を決める |
| ライブラリ・API 仕様の事前調査（ステップ1、`mattpocock-skills:research` の背景エージェント） | 全深度 | `opus` | 公式ドキュメントとソースコードを読み、主張ごとに所有者ソースを特定する |
| 検証 subagent 1巡目（ステップ4） | standard / deep | `sonnet` | 基準が明確な照合。件数が多いので並列に回す |
| 検証 subagent 2巡目（ステップ4） | deep | `opus` | 1巡目で発見不能だった数値の再探索。探索経路の工夫が要る |
| 脚注の振り直し、散文の抽出（ステップ3・6） | 全深度 | シェル | 判断を伴わない変換 |
| 統合、矛盾解消、compress-doc による仕上げ（ステップ3・5・6） | 全深度 | 親 | レポート全体を見渡す必要がある |

## フロー

### ステップ1 — 目次案の承認

plan mode に入り、次の3点を提示して承認を得る。

1. 目次案（大項目と、各大項目に含める中項目）
2. 調査深度
3. 出力先ファイルパス

出力先はユーザーが指定する。指定がなければ提案し、承認を得る。出力先ディレクトリに `NN_*.md` 形式のファイルが既にある場合のみ、次の連番を採番して命名に使う。

目次案を作る前に、テーマの全体像を把握するための予備検索を1-2回行ってよい。この段階で見つけた公式ドキュメントやリポジトリの URL は、ステップ2で subagent に「起点 URL」として渡す。ただしこの段階では本調査を始めない。

承認後、中項目にライブラリ・API・フレームワークの仕様（バージョン、GA 時期、対応プロトコル、設定項目）が含まれるときは、`mattpocock-skills:research` skill を親が起動する。背景エージェントが公式ドキュメント、ソースコード、仕様書を読み、出典付きの Markdown を scratchpad に書く。この結果ファイルのパスをステップ2の subagent に渡す。subagent は Agent ツールを使えないため、この skill を起動できるのは親だけである。

承認を得るまで次のステップに進まない。

### ステップ2 — 並列調査

大項目ごとに調査 subagent を1つ起動する。同時起動は3-5並列に抑える。大項目が6つ以上あるときはバッチに分ける。一斉起動はソースの重複取得とレート制限を招く。並列で起動する subagent は1つのメッセージにまとめて Agent ツールを呼ぶ。

各 subagent に渡すもの:

- 担当する大項目とその中項目
- テーマ全体の1段落説明（他の大項目と重複した調査をさせないため、他の大項目の見出しも併せて渡す）
- ステップ1で見つけた起点 URL（あれば）
- `mattpocock-skills:research` の結果ファイルのパス（あれば）。仕様に関する記述はこのファイルの出典を優先する
- `SOURCE-TIERS.md` と `OUTPUT-FORMAT.md` を読むよう指示
- 結果の保存先パス（scratchpad 配下の `NN_大項目名.md`）

各 subagent の指示に必ず含めること:

- 探索は `SOURCE-TIERS.md` の「一次情報の探索順序」に従う。記事やブログに当たったら、そこに載っている原典 URL をたどり、原典を取得して脚注にする
- 脚注定義には出典種別（`一次統計` / `第三者調査` / `ベンダー自社計測`）を必ず付ける
- 調査結果は保存先パスに書き出す
- 親への返答は「保存先パス」「1行要約」「脚注の件数と、そのうち Tier 1 の件数」の3行のみ。本文を返さない。Tier 1 が半数未満のときは理由を1行添える（一次ソースが存在しない領域か、探索が届かなかったか）
- **Agent ツールを使わない。subagent をさらに起動しない**
- `ax` は `--md --budget` か `--outline` かセレクタを付けて呼ぶ。`--all` と `--body` でページ全文を取得しない
- 取得結果が長いときはファイルに保存し、`grep` / `sed` で必要箇所だけ読む
- ツール呼び出しは1大項目あたり40回程度を目安とする。超えそうなら、確認できた範囲で書き出して終える

親のコンテキストに全文を積むとコンテキストを使い切る。ファイル経由でやり取りする。

subagent が孫を起動すると、消費量が制御不能になる。実測では、再委譲を禁じなかった検証フェーズが1回の調査全体の38%を消費した。

`ax` で取得したページ本文は、以後そのエージェントの毎ターンでキャッシュ読み出しの対象になる。全文取得を繰り返すと、1つの subagent だけでキャッシュ読み出しが数百万トークンに達する。

### ステップ3 — 統合

scratchpad の各ファイルを読み、1つのレポートに統合する。

- 大項目間で重複した記述を排除する
- 脚注ラベルを `[^大項目番号-連番]` 形式に振り直す（`OUTPUT-FORMAT.md` 参照）。振り直しは `sed` / `awk` で行う
- 大項目の間で数値や主張が矛盾している場合は、この時点で解消する。所有者ソースに近い方を採る。解消できないときは両論を併記し、検証ステップに委ねる
- 冒頭メタ情報に一次ソース比率（脚注の総数と Tier 1 の件数）を記載する

各大項目の冒頭に2-3文の導入文を置く。文章の仕上げはステップ6でまとめて行うので、ここでは内容の統合に集中する。

### ステップ4 — 独立検証

quick では実行しない。

検証 subagent を起動する。**本文だけを渡す。参考URL一覧と脚注定義は渡さない。** 書いた本人が自分の拾ったソースを見ながら検証しても、確証バイアスで機能しない。

検証 subagent には `VERIFICATION.md` を読むよう指示する。あわせて、ステップ2と同じ制約（Agent ツールを使わない、`ax` は `--md --budget` かセレクタ付き、取得結果はファイル経由、ツール呼び出しの目安）を渡す。

検証対象の数値が多いときは、章を分けて2-3体の検証 subagent に並列で担当させる。1体に全章を渡すと時間内に終わらない。

deep では2巡実行する。2巡目の subagent には、1巡目で不一致・発見不能だった項目だけを、1巡目が「探索した範囲」と共に渡す。同じ経路を再度たどらせない。

### ステップ5 — 検証結果の反映

検証 subagent の報告に従って本文を修正する。

- 数値が異なっていた → 検証側の値に置換する。元の値と置換後の値を付録Aに記録する
- 一次ソースが見つからなかった → その数値を `数値未確認` に格下げする。項目自体は残す。付録Aに記録する
- 検証側が本文より所有者ソースに近い出典を見つけた → 参考URL一覧の出典をそちらに差し替える
- 全件が確認済みだった → 付録Aを生成しない

ユーザーに個別の判断を求めない。数十件になると承認疲れで素通しされる。

### ステップ6 — 日本語の仕上げ（compress-doc）

統合と検証を終えたレポートに、Skill ツールで `compress-doc` を起動して適用する。人が読み、共有する成果物なので、深度にかかわらず実行する。

```
Skill: compress-doc
args: <レポートの絶対パス>
```

`compress-doc` は節の計測、再構成、圧縮率の機械判定、suiko full を一連で行う。対象ファイルは1つなので、`compress-doc` の手順どおり親が自分で進める。

起動時に、このレポート固有の制約を `compress-doc` の保持域へ加える。

- 脚注ラベル（`[^1-3]`）と、その直前の被参照語
- `（ベンダー自社計測）` のラベルと `数値未確認` の格下げ表現。Tier 判定に関わる語を書き換えない
- 冒頭メタ情報（調査日、対象期間、調査深度、検証カバレッジ、一次ソース比率）
- 参考URL一覧と付録Aは対象節から外す。脚注定義と検証記録は文字数で判定する文書ではない

`compress-doc` 内の suiko full では、`suiko lint` が箇条書き行を解析対象に含めないことに注意する。レポートをそのまま lint すると見出しとラベル行だけが文として扱われ、`low_burstiness` や `uniform_paragraph_structure` の偽陽性が出る。散文の行だけを抜き出した一時ファイルを scratchpad に作り、そちらを lint する。`outline` と `terms` は見出しと箇条書きも対象になるので、レポート本体に対して実行する。

```sh
awk '/^```/{f=!f; next} f{next} /^(#|-|\*|\||>|\[\^|[0-9]+\.)/{next} NF' report.md > prose.md
suiko lint prose.md --genre tech --reading-load --experimental --json
suiko outline report.md --json
suiko terms report.md --json
```

finding を読む前に `doc_char_count`、`readability.particle_token_ratio`、`lexical_diversity.skipped_too_short` を確認する。文字数が実体とかけ離れている、助詞比率が0、`skipped_too_short` が true のいずれかなら、抜き出しに失敗している。

検証済みの数値と出典の対応を崩す修正は却下する。`compress-doc` の `verify` で保持域の差分が出たら元の字面に戻す。

### ステップ7 — 書き出し

承認された出力先に書き出す。冒頭のメタ情報に検証カバレッジ（`数値 42件中 38件が一次ソース確認済`）と一次ソース比率（`脚注 57件中 41件が Tier 1`）を記載する。

書き出し後、ユーザーには次を報告する。

- 出力先パス
- 大項目数と数値の件数
- 一次ソース比率
- 検証で格下げ・置換した件数

## subagent が失敗したときの扱い

レート制限やタイムアウトで subagent が失敗しても、**保存先ファイルが書けているかを必ず先に確認する**。書き出しを終えた直後の終了処理で失敗する場合があり、成果物は無傷なことが多い。

確認するのはファイルの存在と末尾で、`### 参考URL一覧` まで到達していれば完結している。完結していれば再実行しない。

失敗した subagent を無条件に再実行すると、同じソースを取り直して消費量が倍になる。再実行するときは、書けていた範囲を起点 URL と共に渡し、残りの中項目だけを担当させる。

## 参照ファイルの読み分け

| ファイル | 読む主体 |
|---|---|
| `SOURCE-TIERS.md` | 調査 subagent、検証 subagent |
| `OUTPUT-FORMAT.md` | 調査 subagent、親（統合時） |
| `VERIFICATION.md` | 検証 subagent |

親は3つすべてを読む必要はない。ステップ3の統合時に `OUTPUT-FORMAT.md` を読めばよい。

## 使用ツール

| 用途 | ツール |
|---|---|
| ソースの発見 | WebSearch。`site:` で公式ドメインに絞る（`site:docs.example.com`、`site:github.com/org/repo`、`site:investors.example.com`） |
| ドキュメントや記事の読解 | `ax <url> --md --budget 800`。出力が切れたら告知された `--offset` から続きを取る |
| 未知のページの構造把握 | `ax <url> --outline`、`ax <url> --locate "<数値や語句>"`。取得結果は約2分キャッシュされ、探索は無料 |
| 数値や表の抜き出し | `ax <url> <selector> --text`、`ax <url> 'table' --table` |
| ライブラリ・API・フレームワークの仕様 | `mattpocock-skills:research` skill（親がステップ1で起動。背景エージェントが公式ドキュメント・ソースコード・仕様書を読み、出典付き Markdown を書く） |
| リリース履歴 | `ax https://github.com/<org>/<repo>/releases --md --budget 800`、または CHANGELOG の raw URL |

`ax` はURLが既知であることを前提とするため、発見には WebSearch を使う。HTMLに正規表現をかけない。`--all` と `--body` はページ全文をコンテキストに積むので使わない。

## 禁止事項

- Tier 3 ソース（個人ブログ、SEOまとめ記事、AI生成記事、出典のないニュース）の引用
- 記事が引用する数値を、原典をたどらずに記事を出典として載せること
- 出典のない数値の記載
- 装飾目的の図
- ステップ1の承認を得ずに本調査を始めること
- 既存レポートの更新への転用（このSkillは新規作成専用）
