# 出力フォーマット

レポートの構造、見出し階層、脚注、表、図の規則を定める。

## 全体構造

~~~markdown
# <テーマ> — 技術動向調査レポート

> 調査日: 2026-09-02
> 対象期間: 2025-09 〜 2026-09
> 調査深度: standard（独立検証済 / 数値 42件中 38件が一次ソース確認済）

---

## 目次

2. [大項目2のタイトル](#2-大項目2のタイトル)
~~~

## 見出し階層

| 階層 | 記法 |
|---|---|
| 大項目 | `## N. タイトル` |
| 中項目 | `### N.M タイトル` |
| 小項目 | `-` 箇条書き |

`####` は使わない。見出しが4階層になると目次が肥大し、一覧性を失う。

小項目に階層が必要なときは箇条書きのネストで表現する。ネストは2段までに抑える。

## 箇条書きと表

原則としてすべて箇条書きで書く。1行1要点、簡潔に。

**表を使ってよいのは比較軸が3列以上あるときだけ。** 製品比較、パラメータ一覧、階層別の条件など、多次元のデータは箇条書きにすると読解負荷が跳ね上がる。

2列で済む内容を表にしない。「項目 | 説明」の2列表は箇条書きに置き換える。

```markdown
悪い例:
| 項目 | 説明 |
|---|---|
| MCP | Anthropic が標準化したプロトコル |

良い例:
- MCP: Anthropic が標準化したプロトコル
```

## 脚注

### ラベル形式

`[^大項目番号-連番]` を使う。

- 第1大項目の3番目の出典 → `[^1-3]`
- 第4大項目の12番目の出典 → `[^4-12]`

通し番号を使わない。通し番号だと、参考URL一覧を大項目ごとにまとめたときにグループ内で番号が飛び（`[^3] [^17] [^41]`）、章を追加・削除したときに他章の番号がずれる。

Markdown の脚注ラベルは任意の文字列を受理する（GFM、Obsidian ともに `[^1-3]` は有効）。

### 脚注を付ける対象

- すべての数値
- 製品名を挙げた具体的な仕様の記述（GA 時期、対応プロトコル、価格モデルなど）
- 引用した主張

一般的な説明文や、複数ソースから明らかな概念の定義には不要。

### 脚注定義の書式

```
[^1-2]: <発行元> "<タイトル>" <公開日 YYYY-MM-DD>. 〔<出典種別>〕 <URL>
```

出典種別は `一次統計` / `第三者調査` / `ベンダー自社計測` の3種から選ぶ。

公開日が不明なときは `公開日不明` と書く。

### 本文側のラベル

**ベンダー自社計測の数値だけ**、本文に `（ベンダー自社計測）` と明記する。

```markdown
- インシデント解決時間: 最大95%短縮（ベンダー自社計測）[^2-4]
- AIOps市場規模: 2030年に366億ドル[^1-1]
```

一次統計と第三者調査は無印にする。3種すべてを本文に書くと箇条書きの簡潔さが失われる。読者は本文で「盛られた数値」を識別でき、精査したければ脚注へ降りればよい。

## 目次

大項目と中項目の2階層まで載せる。小項目は載せない。

アンカーリンクを付ける。日本語見出しのアンカーは、見出しから記号を除去し、空白をハイフンに置換した形になる。

## 図

ASCII アートを使う。Mermaid は使わない。ASCII は Obsidian でも GitHub でも生のテキストでも読め、diff や grep とも相性がよい。

- **1大項目あたり最大1個**
- 階層構造やコンポーネント構成の説明にのみ使う
- 装飾目的の図は入れない。箇条書きで説明できるなら図にしない

```
                    +-------------------+
                    | Supervisor Agent  |
                    +--------+----------+
                             |
            +----------------+----------------+
            |                |                |
    +-------v------+ +-------v------+ +-------v------+
    | Log Analyst  | | Metric Agent | | Runbook Agent|
    +--------------+ +--------------+ +--------------+
```

## 参考URL一覧

最後から2番目のセクションに置く。大項目ごとにグルーピングし、`### N. 大項目のタイトル` を小見出しにする。

各グループの中で、脚注定義を連番順（`[^N-1]`, `[^N-2]`, ...）に並べる。

複数の大項目で同じソースを参照した場合は、それぞれの大項目のグループに脚注を作る（`[^1-3]` と `[^4-7]` が同じURLを指してよい）。

## 付録A. 検証結果

検証で格下げ・置換が発生したときのみ生成する。全件クリーンなら、冒頭メタ情報のカバレッジ表示（`42件中42件確認済`）で足りる。

~~~markdown
## 付録A. 検証結果

数値 42件を検証し、4件を修正した。

### 置換

- 2.1「インシデント解決時間の短縮率」: 50% → 48%
  一次ソース（PagerDuty 2025年決算資料, 2026-02-11）の値に置換。元の値はベンダーブログの概数表記だった。

### 格下げ

- 1.4「MTTR 改善幅」: 「3倍高速化」→ 数値未確認
  複数のベンダーブログが同一の数値を記載するが、いずれも出典を示さず、一次ソースを特定できなかった。
~~~

## 文体

- 本文は日本語で書く
- 技術用語、製品名、プロトコル名、コマンド、識別子は英語表記のまま維持する
- 各大項目の冒頭に2-3文の導入文を置く
- 箇条書きは体言止めまたは簡潔な断定で書く。「〜と考えられます」のようなぼかしを使わない
