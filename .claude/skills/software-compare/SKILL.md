# software-compare

起動: `/software-compare <ソフトウェア名> <ソフトウェア名> [<ソフトウェア名>...] [出力先ディレクトリ]`

同じ役割を持つソフトウェアを 2〜4 個並べ、ジュニアエンジニアが一読で違いと選び方をつかめる比較ガイドを作る。成果物は次の 4 つで、すべて出力先ディレクトリに置く。

- `<slug>-comparison.md`: 本文
- `images/<slug>-comparison.svg` と `images/<slug>-comparison.png`: インフォグラフィック
- `research-notes.md`: 出典付きの調査メモ

`<slug>` は各ソフトウェア名を英小文字ケバブケースにし、引数の順に `-vs-` でつないだもの（例: `Prometheus` と `VictoriaMetrics` → `prometheus-vs-victoriametrics`）。出力先ディレクトリの既定は、作業ディレクトリ直下の `<slug>/`。

## 0. 対象を確かめる

対象が 1 つだけなら `/software-guide` を案内して終える。5 つ以上なら、4 つに絞るよう頼む。

対象どうしの役割が明らかに違う場合（例: Grafana と Kafka）は、比較が成り立たない理由を一言添えて、このまま進めるか確認する。役割が一部だけ重なる場合（例: Grafana と Kibana）は、重なる役割を比較の軸として明示して進める。

## 1. 調査を背景エージェントに出す

`mattpocock-skills:research` を起動し、その手順どおり背景エージェントに調査させる。依頼文は、この skill の `research-plan.md` の `{{NAMES}}`（対象を「、」でつないだもの）、`{{OUT_DIR}}`（出力先の絶対パス）、`{{DATE}}`（今日の日付）を埋めた全文にする。背景エージェントは会話の文脈を持たないので、依頼文を要約しない。

全対象を 1 体のエージェントに任せる。対象ごとに分けると、比較の軸や機能項目の粒度が揃わなくなるため。

エージェントの報告が届き、`research-notes.md` が出力先にできたらこのステップは完了。届くまでは、ステップ 2 の図の枠組み（色、列の配置、タイトル）だけ先に作ってよい。

調査は長くかかり、エージェントが途中で止まることがある。止まったら新しいエージェントを立ち上げず、SendMessage で同じエージェントを再開させる。再開の指示では、確認済みの事実で先に `research-notes.md` を書き出させ、調べ終えていない項目は「未確認」の行として残させる。

## 2. 図解画像を作る

`research-notes.md` を全部読んでから作る。図は 1 枚の SVG で、1200×800 を基準にする。構成と見た目は `assets/comparison-example.svg`（OpenCost と Kubecost で作った実例）に合わせる。

- 上段: 対象を横に等幅の列で並べる。各列に、名前、一言の位置づけ、特徴を 3 つ置く。特徴は、比較表で対象どうしの差がいちばん大きい行から選ぶ。
- 対象どうしに、組み込み・派生・互換といった関係があれば、列の間に矢印とラベルで示す。
- 下段: 「選び方」として、条件と、その条件で向く対象を矢印でつないだ行を 3〜5 本並べる。本文の「選び方」の箇条書きと同じ順・同じ文言の要約にする。
- 列の色は対象ごとに変え、本文の比較表を読むときにも同じ対象を同じ色で思い出せるようにする。どの対象かを強調色で贔屓しない。
- 文字は図のラベルなので、短い言い切りや体言止めでよい。フォントは `'Hiragino Sans', 'Hiragino Kaku Gothic ProN', 'Noto Sans JP', sans-serif`。

SVG をヘッドレス Chrome で PNG にする。

```sh
cd <出力先>/images && "/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" \
  --headless=new --disable-gpu --hide-scrollbars --force-device-scale-factor=2 \
  --window-size=1200,800 --screenshot=<slug>-comparison.png "file://$PWD/<slug>-comparison.svg"
```

`CVDisplayLinkCreateWithCGDisplay failed` のエラー行は出ても無視してよい。できた PNG を Read で開いて目で確かめ、文字のはみ出し、重なり、枠からの欠けが 1 つも無くなるまで SVG を直して再出力する。

## 3. 本文を書く

`comparison-template.md` の見出し構成をそのまま使い、`<slug>-comparison.md` に書く。コメント（`<!-- -->`）は各節に書く内容の指示なので、書き終えたら消す。

書き方の決まり:

- 文体は「です・ます」。読者はジュニアエンジニアで、専門用語は初出で一言説明する。
- 見出しの直後から本文を始める。ガイドの目的や対象読者を述べる前置きの段落は書かない。
- 事実、数値、バージョン、日付、コマンドは `research-notes.md` にあるものだけを使う。メモで「未確認」になっている事柄は本文に書かない。表のセルだけは「未確認」と書いてよい。
- 公式資料の間で記述が食い違っているとメモにある事柄は、どちらかの値を選ばない。読者の判断に関わるなら、食い違っていることだけを書く。
- コマンドに前提条件（別のソフトウェアが動いていること等）があれば、コマンドの直前に書く。
- 公式のコマンドがそのままでは動かないとき（自分で作るファイルを渡す、namespace が後の手順と合わない等）は、公式の資料で根拠を確かめてから最小限だけ変える。変えた点と理由はコマンドの直前に書き、確かめた根拠は出典付きで `research-notes.md` に追記する。
- 太字は本文全体で 1〜2 箇所。画面のボタン名やメニュー名は「」で囲む。
- 箇条書きは並列の項目（選び方の目安、参考リンク）に限り、理由や条件を含む説明は地の文にする。
- 表の区切り行は `| --- | --- |` の形にする（markdownlint の MD060 対策）。
- 日本語と英単語・数字の間には半角空白を入れる（例: 「Grafana は」「2026 年」「50GB」）。句読点と括弧の隣には入れない。図のラベルも同じ。

比較ならではの決まり:

- 公平に書く。ある観点を 1 つの対象について書いたら、ほかの全対象についても同じ観点で書く。
- 「速い」「軽い」「使いやすい」のような優劣は、調査メモに数値か公式の記述がある場合だけ書き、その根拠を同じ文に添える。
- 開発元が自社の比較ページで述べている内容は、「〇〇の公式サイトによると」と出どころを示して書く。
- 「選び方」は「〜なら X」という条件の形にする。条件は、要件（ライセンス、マネージドで使いたい、既存の構成など）で書き、好みでは書かない。

## 4. レビューする

書いた本文を `research-notes.md` と突き合わせる。次の全項目を確かめ終えたら完了。

- 本文の数値・バージョン・日付・ライセンス名がすべて調査メモと一致している。
- 調査メモに無い主張が本文に 1 つも無い。
- 比較表と機能表のすべてのセルが、調査メモの出典付きの行に対応している。調査メモで「未確認」のセルは「未確認」と書いてある。
- 「違いの詳細」の各小見出しで、全対象に触れている。
- 優劣を述べた文のすべてに根拠がある。開発元の主張には出どころが書いてある。
- 各コマンドが、書かれた前提条件のもとで実際に動く形になっている。
- 「選び方」の箇条書きが図の下段と同じ順・同じ内容になっている。
- `npx -y markdownlint-cli2 --config ~/.config/markdownlint/.markdownlint-cli2.jsonc <本文>` の指摘が 0 件になっている。

見つけた問題はその場で直す。

## 5. yomiyasu で添削する

元の本文をスクラッチパッドへ退避してから、`yomiyasu:yomiyasu` を `tech --full <本文の絶対パス>` で起動し、その手順どおりにリンターと Diff 検査（`--stance=説明`）まで通す。

書き直しは一括で受け入れず、変更ごとに採否を決める。「です・ます」調では、同じ文末が 3 回続くという警告が出やすい。文が自然に読めているなら、警告を消すためだけの言い換えはしない。英単語の前後の半角空白を消すよう求める警告には従わない。比較表と機能表のセルは書き直しの対象にしない。

## 6. 報告する

ユーザーには次の点だけを短く伝える。

- 作ったファイル（本文、画像、調査メモ）のリンク
- レビューと yomiyasu で直した主な点
- 調査メモで「未確認」のまま残った事柄
